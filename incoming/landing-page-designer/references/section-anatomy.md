# Section Anatomy — the app-download page structure

The purpose is fixed (get the store tap), so the structure is fixed too. Eight section types, in this order. Not every page uses all eight — the anatomy tells you what each one buys so you can cut deliberately. Sections are numbered `S1…Sn` in the deliverable.

## The eight sections

### 1. Hero (mandatory)
The only section most visitors read. Must carry, above the fold: the headline (the app's core promise as a *customer outcome*, not a feature), a subhead (who it's for + how the promise happens), the **store CTA** (App Store badge or styled button), and a hero visual placeholder (usually the app on a device). Rule of thumb: a visitor who reads nothing else should still know what the app does, for whom, and how to get it.

### 2. Hook / value expansion (mandatory)
One short section that deepens the hero's promise: the pain named plainly, then the after-state. This is where emotional resonance does its work — the visitor should feel "that's me." Uses PAS or the StoryBrand hero-guide frame (see `copy-frameworks.md`).

### 3. Social proof (mandatory, position flexible)
Ratings, review counts, user counts, press mentions, 1–3 short real reviews. Numbers beat adjectives: "4.8★ from 12,400 runners" outperforms "loved by users everywhere." Every item must be sourced or marked `[NEEDS PROOF — placeholder]`. Position: directly after the hook for unknown apps (borrow trust early); later for apps with a strong brand.

### 4. Feature highlights (mandatory)
3–5 features max, each framed as a benefit with the feature as evidence: outcome first, mechanism second. One line of copy + a visual note each. If the app has more features, they don't go on this page — the App Store listing is the catalog; this page sells the top reasons to tap.

### 5. Screenshots / demo (recommended)
A visual section: screenshot carousel, short demo clip placeholder, or annotated screens. Copy here is captions only — one line each, each caption restating a benefit, never describing the UI ("See exactly when to run" not "The timer screen").

### 6. Objections / FAQ (recommended)
3–5 real objections answered honestly: price, "will this work for me," privacy, "I've tried apps like this before," device/OS support. Source objections from reviews of competitor apps or the app's own materials. An objection dodged on the page becomes an install lost silently.

### 7. Final CTA (mandatory)
The closing ask after the visitor has scrolled everything: restate the core promise in one line + the store badge again. Optionally the lightest-touch urgency that is *true* (a real limited price, a seasonal reason to start now) — never fabricated scarcity.

### 8. Footer trust (mandatory)
Privacy policy, terms, support contact, company name. No persuasion copy — its job is "this is a real company." Required for App Store ad traffic anyway.

## Ordering & cutting rules

- Default order is as numbered. The only common swap: social proof (3) after features (4) when proof is thin.
- Minimum viable page: S1 hero → social proof → features → final CTA → footer. Use it when context is thin — a short honest page beats a long padded one.
- **Traffic-source rule:** paid traffic → hero headline must match the ad's promise (message match), store CTA above the fold, page can be short. Organic/referral → visitor chose to be here; hook and FAQ earn their length. Unknown → design for paid and note the assumption.
- The store CTA appears at least twice (hero + final CTA); on long pages, once mid-page after features.

## Per-section spec fields (what `sections.md` records for each)

Type · purpose (the one job in the scroll narrative) · draft copy (headline/subhead/body/CTA as applicable) · technique applied (which framework/principle from `copy-frameworks.md`) · visual note (placeholder description only) · transition (what pulls the eye to the next section).

S1 (hero) and S2 (hook) additionally require: source (the language-bank line this copy mirrors) — see `customer-research.md` and the `customer-language.md` bank.
